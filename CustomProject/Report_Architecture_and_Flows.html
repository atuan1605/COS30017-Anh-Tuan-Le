Design Rationale and Architectural Designs

This section explains why specific engineering choices were made based on current Android practice, not only what was implemented. It also includes architecture-oriented diagrams (as appendix-ready content): Use Case, Activity Flow, Navigation Flow, Data Flow, and Review CRUD flow.

1) Why These Choices (Current Practice Perspective)

1.1 MVVM + Repository Separation

MVVM was selected to isolate UI from business/data logic and to support maintainability as features expand (authentication, home, detail, favorites, reviews, settings). Repositories centralize API/backend calls, making ViewModels easier to test and reducing coupling between screens and data sources. This aligns with current Android architecture guidance.

1.2 Reactive State with StateFlow/SharedFlow

StateFlow is used for persistent screen state and SharedFlow for one-time events (e.g., logout navigation). This unidirectional state model is preferred over scattered callbacks because it is lifecycle-safe, predictable during screen recreation, and easier to reason about.

1.3 Coroutines and Background Dispatching

Coroutines are used to keep the UI responsive and avoid ANR. IO-heavy work (network/auth) is executed off the main thread where appropriate. This is critical in mobile environments with tighter CPU/battery constraints than desktop systems.

1.4 Single-Activity + Navigation Component

The app uses one host activity with multiple fragments and a navigation graph to simplify flow control and back-stack behavior. This reflects modern Android practice and provides consistent transitions across login/register/OTP/home/detail/settings screens.

1.5 Paging + Caching Strategy

Incremental loading (paging) was chosen over full-list loading to reduce startup latency, memory pressure, and redundant network usage. Cache layers improve perceived performance in unstable network conditions, which is a real-world mobile requirement.

1.6 Dependency Injection (Hilt)

Hilt is used for scalable dependency management and testability. It standardizes object creation (clients, repositories, managers), reducing boilerplate and improving consistency.

5) Suggested Paragraph for Your Report

In this project, architectural decisions were made to align with current Android engineering practice: separation of concerns via MVVM and repositories, reactive state management with flows, and lifecycle-safe navigation control. These choices were not only implementation preferences but responses to mobile-specific constraints such as unstable networks, limited resources, and frequent lifecycle transitions.
